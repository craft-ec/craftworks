FreenetTube on Craftworks

The original FreenetTube streamed one WebM file from a freenet-vfs drive. That stack is retired. Video on Freenet now runs inside Craftworks: the browser encodes a 4K ladder, the network keeps encrypted, erasure-coded pieces, and any page that knows the formats can play it. FreenetTube becomes one more frontend over the same contracts.

Source github.com/craft-ec/craftworks Design docs/ARCHITECTURE.md §6 Runs on any freenet node at /v1/contract/web/B8Y3M8Z3…/

What changed since the first FreenetTube

The first version proved that a page could play a film straight from contract state. It also had limits that a real video site cannot live with: one hand-made WebM, one quality, a single drive owner, a whole SQLite database to open before the first frame, and chunks that a missing peer could make unreadable.

The stack, top to bottom

Everything above the line runs in the viewer's browser tab. Below it, the only thing that exists is a freenet node and the contract states it keeps. There is no server, CDN or index service anywhere in the path.

Playerbrowser
MediaSource with one SourceBuffer per track. Reads the video manifest, chooses a codec family and rung.
MediaCapabilities picks AV1, else HEVC, else H.264. A seek reads only the fragment that holds that time.
Video manifestbrowser
A small JSON file, application/vnd.craftworks.video+json: renditions, their fragment index, poster, scrub strip, pending rungs.
The manifest is itself a file, so it is encrypted and coded like the video.
Filesbrowser
Turns a byte range into chunk reads. Fetches the generation's fragments in parallel, verifies each against the index, decodes on the first 16 that are useful.
Chunk = file size ÷ 16, clamped to 16 KiB–256 KiB. XChaCha20-Poly1305 per chunk. Files up to 64 KiB ride inline in the item.
Items & tablesbrowser
A video is an item of kind video / movie / … in its owner's table: title, about, tags, poster, duration and the file reference.
Every writer has its own feed (a tail plus a tree); readers merge feeds. Comments, votes and subtitles are their authors' items, pointed to from bags.
Keysbrowser + delegate
Public videos are keyed from their content, so the network deduplicates them. Private ones are keyed by their space's salt.
Spaces use MLS; table keys are exports of the epoch secret. The identity delegate on the node keeps the secrets.
WebSocket to the local node · /v1/contract/command
Contractsnetwork
A handful of small WASM contracts, each a primitive: immutable pieces, signed tails, logs, registers, bags and sites.
Contracts never hold keys. They check shape, signatures or proof of work; readers check content against the index.
Freenet nodeevery machine
Stores, routes and serves contract state. Serves the app itself as a web container.
The same site works from any node; links work from any host and custom domains.

Upload: what happens when you press Publish

Probe. Mediabunny reads the file in the browser: duration, tracks, size. The page asks WebCodecs which encoders exist in hardware and plans the ladder.
Poster and scrub strip. A poster frame and a sprite of thumbnails for seeking are drawn from the source.
First rendition, fast. One H.264 rung near 720p is encoded with the hardware encoder and stored. The item posts now, so the video is watchable within the time it takes to encode one rung.
The rest in the background. The remaining rungs are listed as pending in the manifest. Any open page on the uploader's devices takes one at a time under a lease in the account's encodes table. Each finished rung writes a new manifest.
Storing a rendition. The file is cut into chunks, each encrypted, then coded with RLNC in generations of 16. Fragments go up in parallel; a slow put is replaced by a fresh fragment. The index goes up last, so a file is readable only once complete, and an interrupted upload resumes at the same addresses.
Listing. A public video adds a pointer to Discover's bag for its domain and month. Followers and spaces see it through their own reads.

The ladder this Mac makes

A Mac encodes HEVC in hardware, so the efficient family is HEVC + AAC. H.264 is kept only at 720p and 360p as the safety net. Target bitrates from packages/video-studio.js:

A device with an AV1 hardware encoder makes AV1 + Opus instead (9 Mb/s at 2160p). A device with no efficient hardware encoder makes an H.264 ladder alone.

Playback: from a link to the first frame

Open the item. The link names the item by its writer and id. The page reads that writer's table and gets the item, including the file reference { key, root, size, name, type }.
Read the manifest. The reference points at the manifest file. Its index pieces and fragments are fetched from keyed addresses and checked against the root hash.
Pick a rung. MediaCapabilities says which family plays smoothly. The starting rung fits the screen; later fragments switch by measured throughput.
Fetch fragments. A CMAF fragment is a byte range. That range maps to one or two chunks. A healthy file reads each chunk directly, with no decoding; if a piece is missing, the generation is rebuilt from any 16 fragments.
Seek. The fragment index maps time to bytes, so a jump reads only the fragment at the new position.

What is on the network

Every contract is in contracts/, pinned by SHA256SUMS. None of them can read what they hold.

So is FreenetTube another frontend?

Yes. The data model is open: an item row, a file reference, the video manifest, and the piece addresses. A page that implements those formats can list, play, comment on and upload videos that Craftworks users see, and the reverse. Craftworks' own Video app is one lens over that data. A FreenetTube page with a YouTube-like layout would be another, reading the same tables and bags. Nothing about a video belongs to the app that made it.

For a FreenetTube build, the pieces to reuse are packages/files.js (byte ranges over coded pieces), packages/video-player.js (manifest → MediaSource) and packages/video-studio.js (browser encoding). The fastest path is a Craftworks theme plus a page that composes them. A separate site works too, as long as it reads the same formats.

The sample: Big Buck Bunny in 4K

The test upload is the Blender Foundation's open movie (CC BY 3.0): 10 min 35 s, 3840×2160, 30 fps, a 633 MB H.264 source. It is being encoded in a browser on an M4 Max Mac and stored through a freenet node on a Hetzner server, under the account Wren, Craftworks' resident developer.

Open it on any freenet node (replace the host with your own node's):

An earlier attempt stored one generation at a time and ran at 56 KB/s, held back by the slowest put in each generation. Keeping six generations in flight brought it to the link's speed (commit a402b1a). Playback had the same shape: one chunk per round trip. It now fetches a fragment's chunks at once, keeps four fragments in flight, reads most-of-a-generation ranges raced, and offers a quality menu (Auto or any version).
